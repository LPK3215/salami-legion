    它解决什么问题

    品类里的老问题

    军团 / 人群类 IO 游戏的通行规则是接触即整队吞并：两支军团撞上， 人数少的一方一瞬间全没了。于是游戏退化成「谁先变大谁碾压」， 碰撞的瞬间就宣判结果，中间过程没有决策。

    本作把这条规则改掉：接触后每 秒才转移 1 个单位， 逐个持续消耗，直到一方清零。碰撞不再是终点判决，而是一段可以被打断、可以反打、可以撤退的过程。

    由此产生的玩法深度

    • 撤退真的有用：脱离接触会把这对军团的吞噬计时器重置为满，「跑掉再回来」不带半个节拍。
    • 势均力敌会僵持：人数相等时不产生吞噬，只能绕开或先吃掉弱者滚雪球。
    • 多方接触并行消耗：计时器按「军团对」独立维护，被两支队伍夹击时是同时挨两路啃。
    • 数值判断重于操作：绿色标记（人少）冲、红色标记（人多）跑，读盘比手速值钱。

    以上机制描述与实现均出自 js/engine.js 的 updateCombat()，见下方「核心机制」代码原文。

    项选择为什么
    
            
              
    前端原生 HTML + CSS + ES6零构建、零依赖，双击 index.html 就能跑
    
              
    渲染Canvas 2D同屏可达上千小人，DOM 撑不住
    
              
    音效WebAudio 实时合成不需要任何音频素材文件
    
              
    存档localStorage纯前端，无需服务端
    
              
    服务Node 零依赖静态服务器只把静态文件用 http 提供出去，方便预览
    
              
    测试Node + jsdom无头环境里真实执行页面脚本、真实点击 DOM
    
              
    文档图表Node 内置模块生成 SVG / facts数字运行时取自真源，不手写、不引入外部运行时

    无尽模式的生成规则
    
        
    无尽模式没有「层」：只有一份由 makeEndlessLevel() 生成的关卡对象（dynamicWorld: true），
          全程同一场对局，人数只增不减；每满 ENDLESS.step（50）人暂停一次三选一，
          resumeFromMilestone() 直接回到同一场继续。
          地图是以玩家为中心的动态战场（updateDynamicWorld() + streamWorld()，走到哪生成到哪），
          敌军按人数 + 时间每秒对齐，两者都不按层数。
    
        
    
  
    
    
    项规则
    
    
      
    里程碑每满 ENDLESS.step = 50 人 → 冻结对局（status = 'milestone'）→ 三选一 → 原场继续
    
      
    动态地图半径clamp(1500 + 人数 × 1.6, 1400, 2600)，且不小于屏幕对角线的一半；世界框每帧重算为「以玩家为中心、边长 2R」
    
      
    内容存续超出 R × 1.18 的中立小人/装饰物回收，在 0.42R ~ 0.96R 环带补新；无硬边界、无墙
    
      
    敌军支数min(2 + ⌊峰值人数 / 45⌋, 7)，阵亡或溃逃自动补位（1.25R 外判溃逃）
    
      
    敌军人数max(5 + 存活时间 × 0.22, 峰值人数 × 0.30~0.85)（始终略低于我方）
    
      
    成绩记录不写星级，更新 stats.endlessBest（单局最高人数）
    
        
  
    
        
    
        
    公式逐条摘自 js/config.js 的 ENDLESS 常量与 endlessViewRadius / endlessEnemyTarget / endlessEnemyStats，以及 docs/04-development.md §5。

    部署
    
        
    GitHub Pages 经典模式（legacy），发布源是 main 分支的仓库根目录（不是 docs/）：
          git push github main 后自动构建发布，不需要 Actions，也不需要手动触发。
          根目录保留 .nojekyll 以禁用 Jekyll 处理。
    
        
    静态资源都带版本号（如 js/engine.js?v=YYYYMMDD）：Pages 对静态资源给
          max-age=600 强缓存，因此改了 js/ 或 css/ 必须同时改 ?v=，
          否则老访客会继续跑缓存里的旧脚本 —— 普通刷新无效，只有硬刷新（Ctrl+Shift+R）才看得到新版本。
    
        
    本览页在站点上的地址：<站点根>/project_overview/；页内所有资源均为相对路径，子路径下不会 404。

    测试怎么工作
    
        
      
          
    1. 用 jsdom 加载真实 index.html，按 <script> 顺序执行全部游戏脚本；
      2. 
          
    2. 给 Canvas 打桩（jsdom 无绘图能力），其余逻辑全部真跑；
      3. 
          
    3. 模拟真实用户点击，遍历主菜单 / 关卡选择 / 商店 / 成就 / 说明 / 出征准备；
      4. 
          
    4. 进入对局后验证：滑动控制、收编中立小人、逐个吞噬（正向与反向）、技能、暂停继续、通关结算与三选一、关卡推进、无尽模式（动态战场随玩家平移与规模变大、对玩家零边界限制、渲染不画任何边界/场地圈、50 人里程碑暂停三选一后原场继续、人数不重置、全灭结算报峰值人数）、失败流程、商店购买、存档持久化；
      5. 
          
    5. 与时间强相关的用例走 ticks(game, n, dt) 固定步长推进，不依赖 rAF 的墙钟步长，结果可复现；
      6. 
          
    6. 技能/增益「描述 = 实效」校验：构造受控对局逐条量测引擎实际值（7 条增益的数值、6 个技能的范围与秒数），
          防止 desc 变成假承诺；同时断言关卡模式渲染 1 条边界、无尽模式渲染 0 条边界与 0 个场地圈。
      7. 
          
    7. 捕获任何运行期 JS 错误，出现即判定失败。
      8. 
        
    
        
    
          如实记录：这里曾经有一个随机失败的用例，现已修复。
          「应为多帧逐个消耗，而非一次性吞并」原先绑在真实帧推进的墙钟时长上 —— 一批帧耗时超过
           秒时，三次转移会落进同一个快照批次，断言就报
          递减次数=1（同一份主干代码实测失败率约 2/6～3/4，与玩法无关）。
          现在改为固定步长直接驱动 update() + render()
          （ticks(game, n, dt)，步长按秒给），时间基线与帧预算一起换算，连跑多次结果一致；
          同类处理覆盖了反向吞噬、收编中立小人与无尽里程碑。另外，对局内用例会先把第 1 关目标抬高，
          避免移动/摇杆用例顺路吃满人数导致提前通关、后续断言失效。
